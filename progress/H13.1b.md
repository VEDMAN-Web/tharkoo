# H13.1 part 2: photos of any size (Vedant, #357)

## Done
- New `src/lib/image-shrink.ts`: before a photo is sent, the browser reads it (createImageBitmap, EXIF turned the right way up) and, when it is over the upload limit or longer than 2560 px, draws it on a canvas with the long side at most 2560 px and saves it as JPEG (WEBP stays WEBP) at quality 0.85; if it is still over the limit the quality steps down (0.8, 0.75, 0.7) and then the long side (2048, 1600), with one last small try (1280 px, 0.6). Never made bigger; a photo that already fits comes back as the very same file; a see-through PNG gets a white background in a JPEG. No package.
- A photo that cannot be read (broken, unsupported) says "This photo could not be read. Try another photo or take a screenshot of it."
- Used by: the staff upload helper (Create ad, the Media library upload box, the picture picker, import, and the ad edit screen), and the seller post-ad photo step (`uploadMedia` in mediaUpload.ts). The panel's "My photos and videos" page only lists and removes pictures, it has no upload, so nothing changes there.
- The size is no longer refused for photos in: `checkPhoto` (post step), `refusalFor` (Create ad and ad edit), `checkBatch` (Media library and import, new `anySize` option), `fileProblem` (new `anySize` option, used by the picker dialog). Logos, banners and other boxes keep their size rule. The ad photo box now says "any size".
- Server limits unchanged as the backstop (8 MB photo, video limits untouched). The old routes for local development still take under 4 MB.

## Tests changed on purpose (Vedant: photos can be any size)
- tests/e2e/h78-uploader.e2e.ts: the 9 MB file used to be refused ("This photo is 9 MB. The limit is 8 MB."); now it uploads, so four photos are ready and counted; the "refused tile has only Remove" check now uses a file of the wrong type (wrong-type.gif).
- tests/e2e/h7-100-posting.e2e.ts: the 9 MB all-zero file is not a picture, so it is refused as unreadable instead of "too big".
- tests/e2e/h13-1-staff-upload.e2e.ts (my own part 1 test): the 6 MB files are now real pictures made in the page, because every photo is read before it is sent.

## How verified
- tests/server/media/h13-1b-image-shrink.test.ts (7 tests, A5a): 6000 x 4000 comes out long side 2560 as JPEG under the limit; 1000 x 800 under the limit is returned unchanged (same file, nothing drawn); small-in-pixels but big-in-bytes is saved again at its own size; over 2560 px but under the limit is made 2560 px (landscape and portrait); the quality then size ladder; WEBP stays WEBP; unreadable and hopeless files say the plain line.
- tests/e2e/h13-1b-photo-shrink.e2e.ts at 1440: A5b a real 20 MB 6000 x 4000 JPEG on Create ad (the server is asked to sign a file under 8 MB, no error, preview shown) and on the seller post-ad photo step (saved as a smaller picture, no error, preview shown); A5c a broken file shows the could-not-be-read line on Create ad.
