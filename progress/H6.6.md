# H6.6a: Ledger, payment provider interface, coin purchase (mock)

Split: H6.6a (this PR) and H6.6b (withdrawals, payouts queue, TDS/GST admin screen, wallet screens, OTP login). Both are REVIEW PLEASE.

## Done (H6.6a)
- Double-entry, append-only ledger (`src/server/ledger/*`). Accounts: user_wallet, escrow, vendor_earnings, payout_pending, paid_out, platform_revenue, plus `external` (the outside world: coins entering or leaving the site). One transaction is one Mongo document holding all its lines, so lines commit together. Deltas of a transaction must add to zero (checked in code and in a schema pre-validate). Idempotency key per transaction, audit row per transaction.
- Concurrency without Mongo transactions (the test and likely prod Mongo may be standalone): each line has a per-(account, owner) position, and a multikey unique index on `lines.chainKey` means two writers that read the same balance cannot both commit. The loser re-reads and sees the lower balance. Balances are derived by aggregation, never stored or edited.
- One wallet, not two: the user_wallet account is the existing WalletEntry chain (creditWallet/debitWallet). Ledger transactions that touch user_wallet apply that leg through it with a key derived from the transaction key, so a replay finishes any half-applied transaction, and a failed ledger write refunds the wallet debit.
- Coin purchase through `PaymentProvider` (`src/server/wallet/provider.ts`): mock built; cryptoPay and card are stubs that throw with the env names to set (CRYPTO_PAY_API_TOKEN; CARD_PAYMENT_KEY_ID, CARD_PAYMENT_KEY_SECRET). Selected by `COIN_PAYMENT_PROVIDER` (default mock). No real keys.
- Coins are credited only by `POST /api/payments/coins/webhook`: x-payment-signature over "<x-payment-timestamp>.<raw body>", constant-time compare, 300 s window, refusals audited by reason only. Claim-then-credit (pending or failed to succeeded) so a replay or race credits once; the claim is undone if posting fails. Statuses pending, succeeded, failed, refunded. Amount and currency must match.
- Packs are the existing CreditPack rows (credits plus bonus are coins). `GET /api/wallet/coins`, `POST /api/wallet/coins/checkout`, `GET /api/wallet/coins/purchases`.
- Finance settings (`FinanceSettings`): tds %, gst %, coin value (100), min withdrawal coins (5), cooldown days (3). `GET/PUT /api/wallet/admin/settings` for finance/superadmin only, validated, audited. Purchases snapshot TDS/GST for display. No tax logic.
- Escrow helpers (`holdInEscrow`, `refundEscrow`, `releaseEscrow`) for H6.5, and `registerSpendGuard` hook for the people-category guard. No guard ships here.

## Risks
- user_wallet legs and the ledger document are two writes (no Mongo transactions). Replay-safe and compensated, but a crash between them needs a replay to heal; a reconcile job is not built.
- Balances use aggregation over the account's lines: fine now, add a snapshot if an account gets very long.
