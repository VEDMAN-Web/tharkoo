# H7.100: posting works end to end

## Done
- a) A photo that passes the scan is now "cleared" (with clearedAt) instead of staying on "scanning" forever, so publishing no longer fails with MEDIA_NOT_CLEARED. ID documents keep "scanning" (they go through ID review); rejected_csam and rejected_policy are unchanged.
- b) scripts/backfill-cleared-media.mjs: dry run by default, --apply to write. Moves Cloudinary photos stuck on "scanning" to "cleared" with clearedAt = updatedAt. Idempotent. NOT run against any real database.
- c) Member videos: 100 MB and 60 seconds, a 720p mp4 is made by Cloudinary (eager, async) and used for playback. Every failed upload keeps its tile with a red line in plain words and, when a retry can help, a "Tap to retry" button. Photos say 8 MB and JPG, PNG or WebP. The video needs a saved draft first (plain message if not). Imports and admin Create ad keep the old 10 MB and 30 s limits.
- d) Publish errors: every PublishBlockReason has a plain sentence (src/lib/ui/publish-errors.ts); the post page shows it, never the code. VERIFICATION_REQUIRED shows "Verify your ID to publish." with the Verify ID link.

## Not done
- No Cloudinary call is made in the browser tests (they run on local storage); the Cloudinary path is covered by unit tests with a stubbed client.

## Risks
- The 720p delivery URL is c_limit,h_720,w_1280,f_mp4,q_auto for new and old videos; Cloudinary makes older videos on first view.
