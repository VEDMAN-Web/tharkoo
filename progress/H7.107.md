# H7.107 the posting fee debit and refund are atomic

## What was wrong
Two publishes of the same ad at the same moment could both charge the fee (CI failure "expected [ 30, 30 ] to deeply equal [ 0, 30 ]"). The wallet looked for an existing row and then wrote one; both requests passed the check, and the chain key did not stop the second one because it read the first row as its parent.

## The fix (with line numbers)
- `src/server/models/billing.ts:118` adds `refKey` to a wallet row; `:123` is the unique partial index `{ refKey: 1 }` (only rows that have a string refKey are indexed, so every existing row is outside it).
- `src/server/billing/ledger.ts:106` writes `refKey = userId:refType:refId` only when the caller passes `once: true`. Only the posting fee debit (`src/server/billing/posting-fee.ts:74`) and the refund (`posting-fee.ts:98`) do. The fee refId is `listingId:debitCount`, so two parallel publishes of one ad collide; a refund uses the same refId as its debit, so there is one refund per charge.
- (a) A duplicate-key error is handled in `appendEntry`: `ledger.ts:128` swallows it (`duplicateKey`, `:50`) and the loop goes round once more; at `:85` the existing row is found and the call returns `{ balance, created: false }` with the current balance. It does not retry the chain and does not throw, so there is no 500; the caller reports `charged: 0` / refund `0`.
- (b) The index in production: Mongoose `autoIndex` is not switched off anywhere (`src/lib/db.ts` connects with default options), and `readyBilling()` (`ledger.ts:12-27`) awaits `WalletEntry.init()` before every wallet read or write, so the index is built by the first billing call after deploy. Because it is partial, the build cannot fail on old rows. As a belt and braces step there is `scripts/ensure-wallet-index.mjs`: dry run by default (prints the existing indexes of `wallet_entries`), builds the index only with `--apply`, safe to run twice. I have not run it against any real or live database; it is ready, and Opus asks Vedant before it runs on live data.
- (c) Parallel refunds and parallel rejections: tests in `tests/server/billing/posting-fee.test.ts`:
  - two charges at once, 50 rounds, exactly one debit each round (it failed at round 48 before the fix);
  - two refunds at once, 20 rounds, exactly one refund;
  - two moderators rejecting the same ad at once, 10 rounds, one refund;
  - the index script: dry run lists, apply builds the unique `refKey_1` index, second apply does nothing.
