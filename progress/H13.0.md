# H13.0 hotfix: Cloudinary server-side upload with a transformation

## Root cause
`uploadRaw()` in src/server/media/client.ts passed `transformation: options.transformation` (a string of steps) to `cloudinary.uploader.upload`. The Cloudinary Node SDK reads a string given as `transformation` as the NAME of a saved transformation and sends `t_fl_strip_profile/...`, which does not exist, so every server-side upload that had a transformation failed (admin Create ad photos and videos on the legacy route, Bulk import, the watermark migration).

## Fix
The options are now built by `uploadCallOptions()` and the steps go in as `raw_transformation`. Nothing else changed.

## Verified
tests/server/media/h13-0-raw-transformation.test.ts runs the SDK's own `build_upload_params` with no network and no uploader override: the steps string comes out unchanged, does not start with "t_", and keeps `fl_strip_profile` and `l_text:`; the old call shape is shown to produce the "t_" name; and the real `uploadToCloudinary` path (spying on `cloudinary.uploader.upload`) hands the SDK a call whose built parameters carry the steps and no name. Media tests and the connect guard pass.
