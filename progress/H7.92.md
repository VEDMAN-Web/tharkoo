# H7.92: listing indexes

## Done
- Three new compound indexes on the Listing collection, next to the existing status + category + city + published date one:
  - status + state + published date (a state page or a state filter)
  - status + city + published date (a city page or a city filter without a category)
  - status + published date (the feed with no place filter)
- scripts/sync-listing-indexes.mjs: lists the indexes and the missing ones. Dry run by default; `--apply` creates only the missing ones. Needs MONGODB_URI. Not run on any real database.
- tests/server/listings/listing-indexes.test.ts: the schema declares the indexes, a state filter and a city filter use an index scan (no collection scan), the script finds nothing missing, finds a dropped one, and creates only that one.

## Not done
- autoIndex is the Mongoose default (on) in src/lib/db.ts. It is not changed here. See the question below.

## Measured on 200,000 listings (in-memory MongoDB, one run, local)
- Filter on state: about 600 ms before, 56 to 91 ms after.
- Filter on city only: about 9 ms before (already fast), so the city index is a safety net and not needed for speed.
- Filter on status only: about 1.5 s before and after (it returns most of the collection; an index does not help).
- Build time per index: 0.66 to 0.84 s at 200,000 listings.

## Build behaviour
- MongoDB 4.2 and later builds an index without blocking reads and writes except for short locks at the start and the end.
- With autoIndex on, each app instance asks for the missing indexes when it starts; a second request for an existing index does nothing.

## Question for the coordinator
- Production autoIndex: keep it on (the first deploy builds three indexes, under a few seconds at 200,000 listings) or turn it off and run the script once? Nothing changes until the coordinator answers.
