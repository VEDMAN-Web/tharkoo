# H16.2 PR 1: ad code, new ad address, forwards from the old address

Branch: `haiku/h16.2-ad-addresses` (PR 1 of 3). Next PRs: `haiku/h16.2b-link-builders` (every link), then a last PR for the crawl and anything left over after Lane C's sitemap work lands.

## Done

- `src/lib/ad-address.ts` (new, client safe): `generateAdCode` (5 lowercase base36 characters, at least one digit), `isAdCode`, `splitAdSegment`, `adAddress` (`/<category>/<city>/<title-slug>-<code>/`, title slug through the existing `toSlug`, max 60), `parseAdRoute` (area first, then `-<code>`, else other).
- `Listing` model: new `code` (unique, sparse index), `addressPath`, `previousPaths` (max 10, newest last). `code` is made on the first save (`pre("validate")`, also for `insertMany`). Once an ad has a slug, a save that changes title, category or city moves `addressPath` and keeps the old one in `previousPaths`.
- Route `/[category]/[location]/[x]/`: a known area of that city is served first (as today); else `-<code>` finds the ad by its code; a wrong category, city or title part gets a permanent redirect to the right address; an unknown code, a removed or ended ad is not an ad there (404; the proxy answers 410 for gone ads). The ad page itself (`src/app/ad/[slug]/page.tsx`) is still the one implementation, now using the address for canonical, og:url, JSON-LD and the share link.
- Old `/ad/<slug>/` (and the admin-set ad prefix, which is rewritten to `/ad/` first) is forwarded in `src/proxy.ts` to the new address. `/ad/video/...` is left alone. Gone ads still answer 410 first.
- Code fill for ads saved before codes existed: (1) lazily, the first time the old link is opened; (2) on any save through the model; (3) `backfillAdCodes(200)` on every run of the existing cron `/api/cron/expire` (idempotent, guarded by the cron secret, reports `adCodesFilled` and `adCodesRemaining`). No admin screen and no live write is made by this PR.
