# H10.5c-a: "Undo on Settings puts the old value back in the box" (h7-164 d) and a25)

## What 45 is
Not a plan price and not a leaked money setting. 45 is the value the test itself types (`changed = before === "45" ? "46" : "45"`).
The failure was: the box showed the value the test had just typed, after Undo.

## Root cause (product, not the test)
Undo worked in the database every time. The box kept the new value.
- Evidence: in a failing round the database already had edits = 30 (an `settings.undo_windows.undo` audit event existed), while the input still read 45.
- Timeline of a failing round (milliseconds): save answered at 28067, its page refresh at 28069, the Undo click sent its action at 28076 (9 ms later), the refresh after it at 28090. The page data of both refreshes was right (the last one carried 30), yet the box stayed at 45.
- The form was rebuilt from the page (`key` made from the saved values) after every save and Undo. So what the box showed depended on which page refresh the browser applied last. An Undo clicked right after a save (the test clicks it as soon as the toast shows) could lose that race. A person can click that fast too.
- It looked "state dependent" because it needs the Undo within a few milliseconds of the save answering: the slower, busier machine of a full run hit it, a quiet run mostly did not.

## Fix
`src/app/admin/settings/_view/SettingsCards.tsx`: the undo-windows form keeps its own last saved values (`saved`). A save remembers the previous values; when its Undo works, `useAnswer` runs a small `onUndone` callback that puts the box and the saved values back at once. No dependence on refresh order. `SettingsView.tsx`: the `key` that rebuilt the card is removed. `useAnswer.tsx`: `answer(result, message, onUndone?)`, `undo` calls it when the Undo worked. Other cards keep calling `answer` with two arguments, unchanged.
First try, dropped because it did not help (failed again at rounds 2, 4 and 7): a Settings-only undo action that also revalidates the page like the save does.

## Evidence
Same loop (save, click Undo at once, check the box), unfixed build: failed at round 4, 8 (in a 12-run repeat), 4 (with a network log), and 7.
With a 2.5 s pause before Undo: 40 of 40 rounds passed (so the race is the cause).
Fixed build: 100 of 100 rounds passed.
New test `tests/e2e/h10-5c-undo-settings.e2e.ts` does the loop (15 rounds, desktop project).
3 runs in a row on 2 workers (new spec, h7-164, a25-settings, `--repeat-each=3`): see the PR description for the counts.

## Not changed, worth knowing
Other admin cards use their own `useAnswer` with the same "save, then router.refresh()" shape (Prices, Users profile). They have the same kind of race for a very fast Undo; I did not touch them (no failing test, outside this card).
