# H16.1c: city pick lists that stay fast with about 900 cities (part 3 of H16.1)

## The problem
Every place that picks a city used a plain drop-down with every city in it. With about 900 cities that is a very long list, and on a phone it is a full-screen wheel of 900 names.

## What changed
- New `SearchSelect` (src/components/ui/SearchSelect.tsx, search-select.css): a type-ahead box. It shows the best matches only (names that start with what was typed first, then names that contain it), never more than 40 rows, rows 44 px tall, the list is at most half the screen high and scrolls. It is a real combobox: arrow keys move, Enter picks, Esc closes, a tap picks on a phone, leaving the box with a typed name that matches exactly picks it, and clearing the box clears the choice. Two places with the same name (two Aurangabads) show their state beside the name.
- It is used only when a list has MORE THAN 100 choices (`SEARCH_FROM`). The site has 59 cities today, so every screen stays exactly as it is until the cities are imported; then the long lists change by themselves.
- Where it is used:
  - Post ad: both city fields (`SelectField` got an optional `searchOptions`), with two UI-text keys for its words (`post.select.cityType`, `post.select.cityNone`), so the text stays editable.
  - The search pop-up (city box; a state chosen first still gives the short select).
  - Seller profile (city) and Alerts (city; the form is cleared after saving as before).
  - Admin: Listing order (city) and SEO templates (sample city) through `AdminSearchSelect`, which gives it the admin look.
- The address of a city, the value sent to the server and the words on the page are unchanged.

## Tests
- tests/server/layout/h16-1c-search-select.test.ts: the matching rules (starts-with first, contains next, state hint, limit 40) and the place choices.
- tests/e2e/h16-1c-city-pickers.e2e.ts (both sizes, 1440 and 390; puts 907 test cities in the LOCAL database and removes them): the search pop-up shows a text box not a select, shows at most 40 matches in a list that fits the screen with 44 px rows and no sideways scroll, picking sets the city and the search goes to that city; nothing matching says so and Esc puts the old choice back; the post-ad form has the type-ahead, the two same-named places show their state, the keyboard picks (Down, Enter) and Tab keeps it; the alerts page picks a city, saves, shows the alert with the city and clears the form. 6 of 6 pass. Screenshots in .shots/H16.1c/.
- Existing specs on the same build (search, alerts, post step 5) still pass.

## Notes for Opus
- The wizard and the pages read the city list through a cache of up to a minute, so after an import the long lists appear within a minute.
- Every page also sends the city list to the browser (the header and the city-context). With 900 cities that is a few tens of KB of text on each page before compression (not measured here). It is not part of this card (it does not make a picker slow), but it is worth a later card if page weight matters.
- The cities page and the footer lists are not pickers and are unchanged.
