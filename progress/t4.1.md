# T4.1

## Done

- Append-only wallet. Balance is the sum of `delta`. Each insert sets `balanceAfter` to that sum. Rows are never updated. A debit inserts only when the sum stays at least 0, otherwise `402 PAYMENT_REQUIRED`.
- Concurrent debits share one chain key, `chain:{userId}:{previousEntryId}`, on the unique `idempotencyKey`. One insert wins. The other retries and then sees the new balance. Memory Mongo is standalone, so a multi-document transaction is not available. The unique insert is the conditional write.
- `PaymentProvider`: `mock` is the default and returns `pay_test_…` with no network. `razorpay` builds the order body (amount in paise) and throws if `RAZORPAY_KEY_ID` or `RAZORPAY_KEY_SECRET` is missing. A key with the live prefix is refused unless `ALLOW_LIVE_PAYMENTS=true`. That branch never calls `fetch`.
- Pack checkout creates a pending `Payment`. `POST /api/payments/webhook` checks `x-payment-signature` (or `x-razorpay-signature`) as hex HMAC-SHA256 of the raw body using `PAYMENT_WEBHOOK_SECRET`, with `safeEqual`. The same provider event, or a second event for a payment already marked paid, credits the pack once. Pack bonus is a second ledger row.
- Coupons: `percent` or `credits`, `maxRedemptions`, `perUserLimit`, `expiresAt` / `expiry`, `status: active`. Invalid is `404`, expired and used up are `409`. A percent coupon reduces a promotion debit. A credits coupon can be redeemed straight into the wallet. On a pack, either kind becomes bonus credits granted by the webhook.
- Promotions debit the wallet for an owner of an `active` listing and store `startsAt` / `endsAt`. Windows: TOP 1/3/7 days with 3 boosts/day, auto-boost 10 boosts in 6 hours, flash 4 hours (5 boosts in the first hour), other products use their day count. Star capacity is 6 active or pending orders per `cityId`. A full city is `409`.
- `rankScore` and `compareRank` in `@/server/ranking` are pure. Order is star, super-top, flash, top, highlight, new, auto-boost, then verified, then `bumpedAt` or else `publishedAt`.
- `POST /api/cron/boost` requires `x-cron-secret` equal to `CRON_SECRET` (`401` otherwise). It sets `bumpedAt` for due boosts, moves ended active orders to `failed`, and a second call in the same moment is a no-op.
- `POST /api/payments/refund` is limited to `superadmin` or `finance`. It appends a `refund` ledger row and an audit event. Audits do not store the webhook secret or provider keys.

## Not done

- `GET /api/billing/invoices` is outside this task's paths.
- `POST /api/admin/refunds` is outside this task's paths. Refunds are `POST /api/payments/refund`.
- No real Razorpay HTTP client, no live keys, no card data.
- Star has no 12-hour slot field, so the cap is per city, not per slot.
- TOP bumps per day is fixed at 3. The purchase body has no bumps-per-day field.
- A percent coupon does not reduce the rupee pack price. It adds bonus credits after the webhook.
- An abandoned pack checkout still consumes the coupon. There is no reservation expiry.

## Contracts changed

None in `docs/contracts`. Notes for the next task:

- Webhook auth header is `x-payment-signature` (hex HMAC-SHA256 of the raw body). `x-razorpay-signature` is accepted as the same value. Missing or bad signature is `401`.
- Browser mutations use `assertOrigin`. Webhook and cron do not, so a provider or scheduler can call them.
- `POST /api/payments/checkout` body is `{ packId, idempotencyKey?, couponCode? }`. `data` is `{ paymentId, providerRef, balance, provider }`. `providerRef` for mock starts with `pay_test_`.
- `POST /api/wallet/packs` still uses `walletPackBodySchema` and returns `{ paymentId, balance, providerRef }`.
- `POST /api/promotions` body is `{ listingId, productId, durationDays?, idempotencyKey?, couponCode? }`. `POST /api/promotions/checkout` uses `promotionCheckoutBodySchema`. Both return `{ orderId, paymentId, startsAt, endsAt, balance }`. `paymentId` is a wallet `Payment` (`provider: "wallet"`, `currency: "CRD"`).
- `POST /api/cron/boost` returns `{ boosted, expired }` in addition to the contract's `boosted`.
- Coupon messages are `Coupon is invalid`, `Coupon is expired`, and `Coupon is used up`.
- Product `amount` is debited as credits. Seeded amounts are rupees. The product document has no separate credit price.
- Ledger `idempotencyKey` is the chain tip, not the caller's key. The caller's key is `Payment.idempotencyKey`. A ledger operation is unique on `userId + refType + refId`.
- Ranking import: `import { compareRank, rankScore } from "@/server/ranking"`.

## Model gaps

Do not treat these as schema edits. The models were not changed.

- `Listing` has no `bumpedAt`. Cron writes it with the native driver. `rankScore` reads `bumpedAt` only when the caller passes it. Add the field on `Listing` before T5.1 sorts from Mongo.
- `PromotionOrder.status` has no `expired`. Cron sets ended rows to `failed` so they leave the active set and the sweep does not repeat. Add `expired`.
- `PromotionProduct` has no boost count, slot, or duration variant. Those rules live in `src/server/billing/catalog.ts`.
- `Payment.orderId` is required and there is no pack-order collection. A pack checkout stores the credit pack id there.
- Coupons have no redemption collection. Per-user use is audit action `coupon.redeem` plus `redeemedCount`.
- Refund amount is credits, capped by the credits that webhook granted, not by `payment.amount` in rupees.
